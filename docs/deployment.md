# Деплой

Сервіс збирається в один Docker-образ ([`docker/app.Dockerfile`](../docker/app.Dockerfile)):
FastAPI віддає і API, і зібраний веб-інтерфейс, а FFmpeg та gifsicle вже
встановлені всередині. Тому його можна запустити будь-де, де працюють
контейнери. Нижче два найпростіші варіанти.

## Образ

На кожен push у `main` GitHub Actions публікує образ у GitHub Container
Registry:

```
ghcr.io/viktorkorkishko/simple-gif-editor:latest   # останній main
ghcr.io/viktorkorkishko/simple-gif-editor:sha-<коміт>
ghcr.io/viktorkorkishko/simple-gif-editor:1.2.3    # для тегів v1.2.3
```

Якщо пакет приватний, його видимість змінюється в налаштуваннях пакета на
GitHub, або сервер логіниться через `docker login ghcr.io` з токеном, що має
право `read:packages`. Образ можна й зібрати самому:

```bash
docker build -f docker/app.Dockerfile -t simple-gif-editor .
```

Контейнер слухає порт із змінної `PORT` (за замовчуванням `8000`), має
`HEALTHCHECK` на `/health` і працює від непривілейованого користувача.

## Варіант 1: VPS з Docker Compose і HTTPS

Підходить для будь-якого VPS (Hetzner, DigitalOcean, Linode тощо).
[`docker/docker-compose.prod.yml`](../docker/docker-compose.prod.yml)
запускає застосунок за [Caddy](https://caddyserver.com/), який сам отримує
та продовжує сертифікат Let's Encrypt.

1. Встанови Docker і плагін Compose на сервер.
2. Направ DNS-запис `A` (і `AAAA`, якщо є IPv6) свого домену на IP сервера.
   Порти 80 і 443 мають бути відкриті.
3. Склонуй репозиторій і заповни налаштування:

   ```bash
   git clone https://github.com/ViktorKorkishko/simple-gif-editor.git
   cd simple-gif-editor
   cp docker/.env.example docker/.env
   nano docker/.env        # DOMAIN=gif.example.com
   ```

4. Запусти:

   ```bash
   docker compose -f docker/docker-compose.prod.yml up -d --build
   ```

   Щоб не збирати образ на сервері, задай у `docker/.env`
   `IMAGE=ghcr.io/viktorkorkishko/simple-gif-editor:latest` і запусти
   `docker compose -f docker/docker-compose.prod.yml pull app` перед `up -d`.

Сервіс з'явиться на `https://<DOMAIN>` за хвилину, коли Caddy отримає
сертифікат. Логи: `docker compose -f docker/docker-compose.prod.yml logs -f`.

**Оновлення:** `git pull` і та сама команда `up -d --build` (або `pull app`
і `up -d` для готового образу). Compose перезапустить лише змінені
контейнери.

Що робить цей compose-файл:

- застосунок не відкриває порт назовні, до нього ходить лише Caddy;
- коренева файлова система контейнера тільки для читання, завантаження та
  проміжні файли пишуться в окремий том `scratch`, змонтований у `/tmp`;
- Caddy додає заголовки `Strict-Transport-Security`, `X-Content-Type-Options`
  і `Referrer-Policy` та стискає текстові відповіді.

## Варіант 2: платформа для контейнерів

Render, Railway, Fly.io, Google Cloud Run, Koyeb та подібні вміють
запускати образ напряму або збирати його з репозиторію.

- **Dockerfile:** `docker/app.Dockerfile`, контекст збірки корінь репозиторію.
  Або готовий образ з GHCR.
- **Порт:** платформа зазвичай сама передає `PORT`, образ його підхоплює.
- **Health check:** `GET /health`.
- **HTTPS** дає платформа, Caddy не потрібен.
- **Змінні:** див. таблицю нижче. Якщо платформа ставить свій проксі,
  задай `FORWARDED_ALLOW_IPS="*"`, щоб у логах були справжні IP клієнтів.

Зверни увагу на обмеження платформи щодо розміру запиту й часу відповіді:
конвертація довгого фрагмента з цільовим розміром може тривати десятки
секунд, а відео має пройти цілком одним запитом.

## Налаштування

| Змінна                | За замовчуванням | Опис |
|-----------------------|------------------|------|
| `MAX_UPLOAD_MB`       | `100`            | максимальний розмір відео; більші запити відхиляються з `413` ще до завантаження |
| `MAX_CLIP_SECONDS`    | `60`             | максимальна тривалість GIF після обрізання; `0` вимикає ліміт |
| `MAX_CONCURRENT_JOBS` | `2`              | скільки конвертацій і прогнозів виконується одночасно |
| `JOB_WAIT_S`          | `30`             | скільки запит чекає на вільне місце, перш ніж отримати `503` |
| `FFMPEG_TIMEOUT_S`    | `120`            | ліміт часу на один запуск FFmpeg |
| `PORT`                | `8000`           | порт, який слухає сервер |
| `FORWARDED_ALLOW_IPS` | `127.0.0.1`      | з яких адрес довіряти заголовкам `X-Forwarded-*` |
| `TMPDIR`              | `/tmp`           | куди пишуться завантаження та проміжні файли |

## Ресурси

Кожна конвертація це окремий процес FFmpeg, який займає одне-два ядра
і до кількох сотень МБ пам'яті, залежно від ширини GIF і тривалості
фрагмента. Хороша відправна точка: `MAX_CONCURRENT_JOBS` дорівнює кількості
ядер, і не менше 1 ГБ пам'яті на кожну одночасну конвертацію. Сервер з
2 ядрами та 2–4 ГБ пам'яті спокійно тримає значення за замовчуванням.

Місце на диску: кожен запит тримає завантажене відео й проміжні файли, доки
не завершиться, тобто приблизно `MAX_UPLOAD_MB` × (`MAX_CONCURRENT_JOBS` +
запити в черзі). Тимчасові теки видаляються після кожного запиту, а ті, що
лишилися після аварійного завершення процесу, прибираються під час старту.

Ліміт діє в межах одного процесу. Щоб обробляти більше запитів, запусти
кілька контейнерів за балансувальником, кожен зі своїм `MAX_CONCURRENT_JOBS`.

## Свій зворотний проксі

Якщо замість Caddy стоїть nginx чи інший проксі, перевір три речі:

- ліміт тіла запиту не менший за `MAX_UPLOAD_MB` (у nginx `client_max_body_size 110m;`);
- тайм-аут читання відповіді достатній для довгих конвертацій
  (у nginx `proxy_read_timeout 300s;`);
- проксі передає `X-Forwarded-For` і `X-Forwarded-Proto`, а в застосунку
  задано `FORWARDED_ALLOW_IPS` з адресою проксі.
